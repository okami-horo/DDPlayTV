## Interface and ordering rules

- C owns stable descriptors, launch options, request/verification service contracts and read-only projections. S extracts references and resolves protocol resources. P owns the request store, PreparedPlayback and ActivePlaybackSession. A adapts platform services. No feature-to-feature dependency is added.
- `PlaybackRequestService : IProvider` submits stable inputs and handles verification operations by opaque ID. Its process-shared implementation and store hold no Activity or kernel. `PlayerViewModel` retains the active session across configuration recreation.
- Move `Media3LaunchParams` to `PlaybackLaunchOptions`, retaining `mediaId`, `sourceType`, `requestedCapabilities` and `autoplay`. The provider atomically submits descriptor/options/origin. Navigation carries only `requestId`; recovery carries only binding IDs; verification navigation carries only `verificationId`.
- `sessionId` is the first request ID and remains stable until explicit exit. Increment `sourceRevision` on source/transport replacement, not on progress saves. Internal changes retain `lastCommittedRequestId`. A kernel-only fallback reuses the lease and changes the runtime profile.
- ActivePlaybackSession serializes commands/events on the playback thread; network, encryption, persistence and blocking cleanup run off that thread. A single store update order guards pending/verification/snapshot changes. Keep actual runtime revision separate from the last persisted revision.
- Controlled replacement: prepare, reconcile/remove native candidate, recheck request/TTL/runtime revision, save snapshot and consume matching pending in one encrypted value, apply backend change, retire detached old source. Failure before commit preserves old playback; failure after commit follows existing recovery and has no promised rollback.
- Native automatic transition: candidate stays in memory; enqueue without a disk write; on a verified actual transition adopt runtime ownership first, then save. Save failure keeps playback running and retries the latest state. Process recovery may return to the preceding successfully saved episode.
- Release follows session → PreparedPlayback → Source → Addon/lease → underlying resources. PreparedPlayback delegates source release. Addon cancels its own work; only the lease removes its Bilibili token. During queue cancellation, release a candidate only after confirmed removal; if it has already become current, adopt it as active and retire it only after a later backend detachment.
